# Runbook — theygrow-app

Operational reality of `theygrow-app` today, plus the live-infra divergence note. This file is the single source for live-infra identifiers — the contract files (`AGENTS.md`, `CLAUDE.md`) keep their guardrails as unnamed file paths and link here instead.

## What runs today

The product in production is a **static PWA** served by nginx and deployed on GCP Cloud Run. The served PWA assets live under `/app` (the M2-P1 monorepo split moved them there from the repository root); in M2-P3 the build-config relocated from the repository root into the owning subtrees — PWA build-config under `/app`, API build-config under `/api`. The `/api` backend now deploys as **its own Cloud Run service** on its own URL (see below).

- Entry point: `app/index.html` — the app shell. Since A1-P5 the only JS still inline in it is the `<head>` gtag/`trackEvent` shim (which the inline `onclick` on the Telegram link requires) and the PWA install-prompt IIFE (left inline deliberately: `beforeinstallprompt` is unobservable to the parity suite, see `A1-DL-006`). Everything else lives under the module mount.
- PWA assets: `app/manifest.json`, `app/sw.js`, `app/offline.html`, `app/icons/`.
- Module mount: `app/m/v{N}/` served at `/m/v{N}/` — the versioned home of everything extracted out of the shell (today `app.css`, `sw-register.js`, the app entry `app.js`, the `core/` modules holding shared state, I/O and pure helpers, and the `surfaces/` modules holding one file per UI surface). The shell **executes** three of these — `app.css`, and `sw-register.js` and `app.js` as its two `<script type="module">` entries; everything under `core/` and `surfaces/` is reached through `import` statements, which is why the ship-list guard walks the import graph (`A1-P4-INV-001`). Since A1-P6 the shell also **names** each of those fifteen modules in a `<link rel="modulepreload">` hint, which collapses the cold-boot fetch waterfall from four discovery waves to one. A hint is a delivery instruction, not an entry: `modulepreload` fetches and compiles but never evaluates, so the graph still boots from `app.js` alone, and the guard deliberately does not treat hints as walk roots. The hint set is asserted equal to the walked graph in both directions (`A1-P6-INV-001`). See `A1-DL-007`. **Version-in-path**, so the bytes at a published URL never change: a content change ships as a **new** mount version and the old one stays on disk, byte-untouched. Served immutable by the generic static nginx location and precached by the SW; bumps are owner-run — see **Module mount** below. See `A1-DL-004`, `A1-P3-INV-001`.
- KB artifact: `app/kb-v1.json` — the vendored, versioned domain-KB artifact (vault ADR-026; curation home is the separate `theygrow-domain-kb` repo). The app is a pure READER: it boots by fetching `/kb-v1.json` (no inline data copy since VDK-P3). Served immutable by nginx (versioning-by-filename, vault ADR-024) and precached by the SW. Consumed byte-as-published (`VDK-P3-INV-001`); re-vendoring and version bumps are owner-run — see **KB artifact** below. See `VDK-DL-001`.
- App icons (install surface): the brand icon/favicon set under `app/icons/` — manifest `purpose: "any"` 192/512 (`icon-logo-192-v2.png` / `icon-logo-512-v2.png`) + `purpose: "maskable"` 192/512 (`maskable-192-v2.png` / `maskable-512-v2.png`), the `<head>` `rel="icon"` PNGs `favicon-16/32.png` + `rel="apple-touch-icon"` `apple-touch-icon-v2.png` (180×180) — all precached by `app/sw.js` (`CACHE_VERSION v9`, which also delivers them to installed clients via the network-first SW + `#updateBanner` path). A discrete `favicon.ico` is intentionally **absent** (PNG-only): the PNG `rel="icon"` links cover the browser tab and the bare `/favicon.ico` probe 404s harmlessly. The assets use a new-filename scheme, so a `CACHE_VERSION` bump re-fetches them fresh (versioning-by-filename, vault ADR-024); superseded files stay on disk, dereferenced, and are never rewritten in place. See `ICON-DL-001`, and `A0-DL-001` for the `-v2` set.
- Icon master (build-time source, **not** served at runtime and **not** precached): `app/icons/splash-logo-name-1024.png` — owner-supplied 1024×1024 logo+name lockup, opaque RGB on `#FFFFFF`, content inside a 318 px radius of centre (fits both the Android 12+ circular splash crop and the maskable 80% safe zone). Every `-v2` install-surface icon is a plain Lanczos downscale of it (`Image.resize((N,N), Image.LANCZOS)`, `save(optimize=True)`) with no geometry change — re-derive from the master rather than editing a derived icon. The Android splash is generated by the OS from `manifest.json` (`background_color` `#FFFFFF` + the maskable icon); on Android 12+ the system splash renders **no** app label, which is why the name is baked into the icon. An installed WebAPK only picks up manifest changes on Chrome's own update check (can lag ~a day) — to verify a splash change immediately, uninstall and reinstall the PWA. See `A0-DL-001`.
- Update delivery: the service worker (`app/sw.js`) serves the app shell **network-first**, so an installed client picks up the freshly deployed `app/index.html` on its next navigation (no hard-refresh); a newly installed worker parks in `waiting` and the page surfaces an in-app "Обновить" banner (`app/index.html`) — the user drives activation rather than the worker auto-applying. See `PWA-DL-001`.
- Web server: nginx (configured by `app/nginx.conf`) inside the container.
- Cache surface: the per-path `Cache-Control` headers — including `/sw.js` `no-cache, must-revalidate` (so a redeployed worker is always re-fetched) — live in `app/nginx.conf`. `app/cloudbuild.yaml` carries **no** cache directives; cache behaviour is entirely an nginx concern.
- Container: `app/Dockerfile` (nginx-based).
- CI / CD: GCP Cloud Build — `app/cloudbuild.yaml` builds/deploys the PWA; `api/cloudbuild.yaml` builds/deploys the production `/api` service; `api/cloudbuild.staging.yaml` builds/deploys the `/api` **staging** service (A2-P1).
- Hosting: GCP Cloud Run — **two** services running today: the PWA and production `/api`. The staging `/api` contour is **not raised**: A2-P1 landed its build-config and this file carries its procedure, but no staging Cloud Run service, trigger, database, role, secret, runtime service account or seed exists (see **Staging contour** below).

The Python / FastAPI backend (`/api`) skeleton landed in M2-P2; in M2-P3 it gained its deploy path and now runs **deployed** as its own Cloud Run service (own image + build-config + trigger), with `/api/health` green on its own URL. Since **A3-P1** it is **private** (`--no-allow-unauthenticated`) and reachable only **through the PWA's nginx**: origin unification landed in A3-P1, not M5 as originally scheduled (`A3-DL-001`; the M5 assignment came from `M2-DL-002`). The browser talks only to the PWA origin, the PWA container proxies `/api/*` service-to-service with a metadata-minted ID token, and **no CORS header is issued anywhere**. See **Same-origin `/api` proxy** below.

## Build + deploy path

The deploy is fully driven by Cloud Build. There are **three self-contained build-configs** — one per app, plus the `/api` staging sibling — each designed to run on its **own** Cloud Build trigger with an `includedFiles` path filter, so a change in one subtree never rebuilds the other. **Two** of those triggers exist (the PWA and production `/api`); the staging trigger is described below and has not been created. See the build-config files for the canonical build steps; do not duplicate them here.

- **PWA:** `app/cloudbuild.yaml` builds the container from `app/Dockerfile` (build context `app/`), pushes to Artifact Registry, deploys to the PWA Cloud Run service — public (`--allow-unauthenticated`): it is the product's front door. Trigger: push to `main`, `filename = app/cloudbuild.yaml`, `includedFiles = app/**`. Since A3-P1 it carries **two trigger substitutions** — `_API_UPSTREAM_URL` (the prod `/api` base URL, which is both the proxy target and the ID-token audience) and `_PWA_RUNTIME_SA` (the service account the PWA runs as, and the identity that holds `roles/run.invoker` on prod `/api`) — plus a Step 0 that fails the build when either is empty. Both are live identifiers and are **not** in the repo. See **Same-origin `/api` proxy** below.
- **`/api` (production):** `api/cloudbuild.yaml` builds from `api/Dockerfile` (build context `api/`), pushes to Artifact Registry, deploys to the production `/api` Cloud Run service with `--no-traffic --tag sha-$SHORT_SHA` (A2-P1 — see **Promotion + rollback (`/api`)** below) and, since A3-P1, `--no-allow-unauthenticated`: production `/api` is **private**, invoked only by the PWA container's proxy. Trigger: push to `main`, `filename = api/cloudbuild.yaml`, `includedFiles = api/**`, `ignoredFiles = api/cloudbuild.staging.yaml`. **Since A3-P2 the production deploy is database-wired**: `--add-cloudsql-instances`, `--set-secrets DATABASE_URL`, `--service-account` (a dedicated least-privilege runtime account) and `--max-instances 2`, with the three live identifiers arriving as trigger substitutions behind a Step 0 guard. Before A3-P2 it passed none of them and its whole served surface was `/api/health`, which needs no environment; `GET /api/health/ready` is the route that changed that. Setting up the instance, the secret, the role and the grants is **Production database enablement** below — and note the ordering there: the substitutions are set **after** merge, the same rule **Same-origin `/api` proxy** carries, for the same `MUST_MATCH` reason.
- **`/api` (staging) — committed, never run:** `api/cloudbuild.staging.yaml` builds the same `api/Dockerfile` and context, pushes a **distinct image name** (`api-staging`) to the same Artifact Registry repository, and would deploy the staging Cloud Run service — private (`--no-allow-unauthenticated`), Cloud-SQL-attached, `DATABASE_URL` from Secret Manager, its own least-privilege runtime service account, `--max-instances 2`. It carries **no** `--no-traffic`/`--tag`: staging *is* the smoke contour. Trigger **to create**: push to `main`, `filename = api/cloudbuild.staging.yaml`, `includedFiles = api/**`, `ignoredFiles = api/cloudbuild.yaml` — it does not exist, so this build-config has never executed. Live identifiers would arrive as trigger substitutions and are not in the repo. See **Staging contour** below.
- **Promotion gate (L1, ADR-020).** `app/cloudbuild.yaml` Step 3 deploys the PWA with `--no-traffic --tag sha-$SHORT_SHA`, so each push lands a 0%-traffic, sha-tagged revision and the live revision keeps serving until the owner smoke-tests and promotes. Since A2-P1 `api/cloudbuild.yaml` carries the same gate for production `/api`. The two have separate procedures — see **Promotion + rollback (L1 deploy-safety gate)** and **Promotion + rollback (`/api`)** below.
- **Staging contour (L2, ADR-020 as amended).** ADR-020 originally rejected a standalone staging service, on the reasoning that a per-revision `--no-traffic --tag` gives an addressable zero-traffic revision of the *same* service (`L1-DL-001`, alternative 2 — history, unamended). That holds for the single-file PWA and does **not** hold for a database-backed backend: a zero-traffic revision of the production service still points at the production database, so there is nowhere to exercise a retrieval or migration change safely. The amendment adds a dedicated staging service on a **separate database on the same Cloud SQL instance**, seeded from synthetic data only. See **Staging contour** below (`L2-DL-001`).

### Promotion + rollback (L1 deploy-safety gate)

> **Owner GCP action.** Every `gcloud` command below is run by the owner against the live project — Claude Code does not run them. The PWA Cloud Run service `child-tracker-service` and region `europe-west1` are the live-infra identifiers carried in this RUNBOOK (see "Live-infra divergence"); the contract files do not name them.

1. **What the deploy does.** `app/cloudbuild.yaml` Step 3 deploys `child-tracker-service` with `--no-traffic --tag sha-$SHORT_SHA`. Each push lands a fresh revision at **0% traffic**, reachable only via its **per-revision** `sha-<SHORT_SHA>` tagged URL. The live revision is untouched until promotion.
2. **Get the tagged URL.** The tag is per-revision (sha-specific), so smoke the *just-deployed* revision — not a persistent URL. Read the tagged URL from the Cloud Build deploy log, or:
   `gcloud run services describe child-tracker-service --region europe-west1 --format 'value(status.traffic)'`
   (the tagged URL has the form `https://sha-<SHORT_SHA>---child-tracker-service-<hash>.europe-west1.run.app`).
3. **Smoke the tagged revision** (owner/manual, no JS toolchain) — against the tagged URL `$TAG_URL`:
   - Health: `curl -fsS "$TAG_URL/" -o /dev/null -w '%{http_code}\n'` → `200`.
   - Live-DOM (app shell served): `curl -fsS "$TAG_URL/" | grep -q '<title>Child Dev Tracker</title>'` → exit 0.
   - Live-DOM (update banner present): `curl -fsS "$TAG_URL/" | grep -q 'id="updateBanner"'` → exit 0.
   - Worker re-fetched fresh: `curl -fsSI "$TAG_URL/sw.js"` → `200` with `Cache-Control: no-cache, must-revalidate` (the `/sw.js` header from the cache-surface note above).
   - KB artifact immutable: `curl -fsSI "$TAG_URL/kb-v1.json"` → `200` with `Cache-Control: public, immutable, max-age=31536000` (the narrow `^/kb-v[0-9]+\.json$` nginx location).
   - Module mount immutable + MIME (the only place production `Content-Type` is ever observed — it comes from the base image's `mime.types`, which is not in this repo and which no test parses): `curl -fsSI "$TAG_URL/m/v1/app.css"` → `200` with `Cache-Control: public, immutable, max-age=2592000` and `Content-Type: text/css`; `curl -fsSI "$TAG_URL/m/v1/app.js"` and `curl -fsSI "$TAG_URL/m/v1/core/state.js"` → the same `Cache-Control` and a **JavaScript** `Content-Type` (`application/javascript` on the current base image; `text/javascript` is equally valid — anything else blocks the ES module outright). `app.js` is the shell's only JS entry and a `core/` file proves the subdirectory is served by the same rule; `/m/v1/sw-register.js` carries the same headers. Repeat for the current mount version after a bump.
   - KB artifact integrity (ADR-020 gate): `curl -fsS "$TAG_URL/kb-v1.json" | sha256sum` → must equal `sha256sum app/kb-v1.json` at the deployed commit (served == vendored, byte-as-published; for the current artifact: `03a71f2e6336095d0e7fa8ffd575e32bceae8d557e5c8e721e28c40537dcc9ab`).
4. **Promote.** Shift 100% traffic to the just-smoked revision:
   `gcloud run services update-traffic child-tracker-service --to-latest --region europe-west1`.
5. **Rollback / abort.**
   - **Abort (no promotion):** do nothing — withholding promotion leaves prod on the prior revision (the no-traffic revision serves no users).
   - **Roll back after promotion:** pin traffic to the previous good revision:
     `gcloud run services update-traffic child-tracker-service --to-revisions <prev-revision>=100 --region europe-west1`.
6. **Tag accumulation.** Promotion does **not** remove the `sha-` tag, so tags accumulate across deploys. They are harmless (each just routes 0% traffic to an old revision) and are pruned **out-of-band** by the owner when desired — e.g. `gcloud run services update-traffic child-tracker-service --remove-tags sha-<old> --region europe-west1`, or delete the stale revision outright (`gcloud run revisions delete <rev> --region europe-west1`). No automated pruning this packet.

### Promotion + rollback (`/api`)

> **Owner GCP action.** Every `gcloud` command below is run by the owner against the live project — Claude Code does not run them. The production `/api` Cloud Run service `theygrow-api`, the staging service `theygrow-api-staging` and region `europe-west1` are live-infra identifiers carried in this RUNBOOK (see "Live-infra divergence"); the contract files do not name them.

This mirrors the PWA gate above, with four deliberate differences — read them before treating the two procedures as interchangeable.

1. **Check what is actually serving — start here, not at the tagged URL.** Since A2-P1 `theygrow-api` never auto-updates, and unlike the PWA there is **no visible signal** that it is stale: the whole served surface is one static JSON body, so a six-week-old revision looks exactly like a fresh one. Read the real state first:
   `gcloud run services describe theygrow-api --region europe-west1 --format 'value(status.traffic)'`.
   A backlog of unpromoted revisions is normal and harmless, but it must be a fact you looked up, not one you assumed.
2. **What the deploy does.** `api/cloudbuild.yaml` Step 3 deploys `theygrow-api` with `--no-traffic --tag sha-$SHORT_SHA`. Each push lands a fresh revision at **0% traffic**, reachable only via its **per-revision** `sha-<SHORT_SHA>` tagged URL. The live revision is untouched until promotion. **One-time behaviour on the first such deploy:** if the service is currently in latest-traffic mode, the first `--no-traffic` deploy pins traffic to the then-current revision. Verify with the `describe` in step 1 rather than assuming — the transition happens once and is invisible afterwards.
3. **Get the tagged URL.** The tag is per-revision (sha-specific), so smoke the *just-deployed* revision — not a persistent URL. Read the tagged URL from the Cloud Build deploy log, or from the same `describe` output as step 1 (the tagged URL has the form `https://sha-<SHORT_SHA>---theygrow-api-<hash>.europe-west1.run.app`).
4. **Smoke the tagged revision** — against the tagged URL `$TAG_URL`. Today this is honestly **one** assertion, because `GET /api/health` is the entire deployed surface:
   - Health: `curl -fsS "$TAG_URL/api/health"` → `{"status":"ok","service":"theygrow-api"}`.
   Since A3-P1 the service is private, so that `curl` needs an identity token — `curl -fsS -H "Authorization: Bearer $(gcloud auth print-identity-token)" "$TAG_URL/api/health"` — or run it through `gcloud run services proxy`. An unauthenticated `curl` returning `403` here is the service behaving correctly, not a broken revision.
   Do not pad this list to look like the PWA's. Extend it when the served surface grows — any route beyond `/api/health` is the trigger. (The same-origin proxy, formerly named here as the other trigger, landed in A3-P1; its own smoke lives in **Same-origin `/api` proxy** below and asserts the *proxied* path from the PWA side.)
5. **The eval precondition is a convention, not a mechanism — and today it cannot be satisfied at all.** For a backend change the intended gate is: **step 12 of the staging contour below — `theygrow-eval --mode staging` — has been run against staging and exited `0`** *before* this revision is promoted. The contour has never been raised, so there is nothing to run it against: until it is, every promotion happens with this precondition unmet, and that is the current state rather than an exception. Even once raised, nothing enforces it. If the staging build fails outright, the production build still succeeds and still lands a promotable 0%-traffic revision; and nothing anywhere reads the eval's exit code or its scorecard on the way to the promote button. A failed or unrun staging eval is something the owner must **notice**, not something that blocks the button. Automating it is deferred (`L2-DL-003`).
   Know what a green run does and does not license. It says a change did not break retrieval fusion, note-only eligibility, community scoping, the grounding gate or honest degradation **on a fixed synthetic corpus with in-perimeter stand-in providers**. It says nothing about Russian lexical recall, embedder quality or answer faithfulness — those need the real corpus and cleared real providers, which is the M4-CLOSE mini-eval, not this. A green scorecard is not evidence for either named port-out trigger (`M4-DL-001`, `M4-DL-004`); the scorecard says so in its own body.
6. **Promote.** Pin traffic to the revision you actually smoked:
   `gcloud run services update-traffic theygrow-api --to-revisions <smoked-revision>=100 --region europe-west1`.
   This deliberately differs from the PWA section's `--to-latest`: `--to-latest` returns the service to latest-traffic mode and can be defeated by another deploy landing between the smoke and the promotion, whereas naming the revision cannot.
7. **Rollback / abort.**
   - **Abort (no promotion):** do nothing — withholding promotion leaves production on the prior revision (the no-traffic revision serves no users).
   - **Roll back after promotion:** pin traffic to the previous good revision:
     `gcloud run services update-traffic theygrow-api --to-revisions <prev-revision>=100 --region europe-west1`.
8. **Tag accumulation.** Same as the PWA gate: promotion does not remove the `sha-` tag, tags are harmless, and pruning is out-of-band (`--remove-tags sha-<old>`, or delete the stale revision).

## Same-origin `/api` proxy (A3-P1, owner-run)

> **Owner GCP action.** Every `gcloud` command and console step below is run by the owner against the live project — Claude Code does not run them and does not touch GCP. The PWA Cloud Run service `child-tracker-service`, the production `/api` service `theygrow-api` and region `europe-west1` are live-infra identifiers carried in this RUNBOOK (see "Live-infra divergence"); the contract files do not name them.

What A3-P1 changed, in one paragraph: production `/api` deploys `--no-allow-unauthenticated`, and `app/nginx.conf` gained a `location ^~ /api/` block that reverse-proxies to it, replacing the upstream `Authorization` header with an ID token minted at container start from the metadata server (`audience` = the prod `/api` service URL) and refreshed by `app/docker-entrypoint.sh`. The browser reaches `/api` only same-origin; **no CORS header is issued anywhere**, by construction (`A3-P1-INV-001`).

**The steps below are strictly ordered. Steps 1–2 happen BEFORE the packet is merged; the trigger substitutions (step 4) happen AFTER.** The first half is IAM: merging flips production `/api` to authenticated-only immediately, so the invoker binding cannot lag behind it. The second half is Cloud Build's `MUST_MATCH` substitution option, kept deliberately in `app/cloudbuild.yaml`: a trigger that supplies a key the build-config on `main` does not declare fails **every** build until the packet lands, so setting the substitutions early breaks `main`. **Production database enablement** below carries the same ordering rule for the same reason — the two procedures do not differ here.

1. **Create or designate the PWA runtime service account, and let Cloud Build act as it.** It must be a **dedicated least-privilege** account — explicitly **not** the project-default compute service account, which is shared by every default-SA workload in the project and would therefore turn step 2's grant into project-wide access to `/api`. This mirrors the staging runtime SA (ADR-020, "Staging contour" step 6), which is the governing precedent. Then let the Cloud Build service account impersonate it, or the deploy fails with an `actAs` permission error rather than anything that names the real cause:
   `gcloud iam service-accounts add-iam-policy-binding <pwa_runtime_sa> --member serviceAccount:<cloudbuild_sa> --role roles/iam.serviceAccountUser`.
   Record the account name under "Live-infra divergence" below.
2. **Grant that account `roles/run.invoker` on production `/api` — before anything else can call it.**
   `gcloud run services add-iam-policy-binding theygrow-api --member serviceAccount:<pwa_runtime_sa> --role roles/run.invoker --region europe-west1`.
   This is a **service-level** binding, not a per-revision one, so it must exist before *any* PWA revision carrying the proxy takes traffic. Two independent reasons it cannot wait: merging the packet fires the `/api` trigger, whose deploy applies `--no-allow-unauthenticated` to the service the moment it runs (service-level IAM — the `--no-traffic` split does not defer it); and a promoted PWA revision without this binding serves every `/api/*` request as `403` to real users.
3. **Merge the packet.** This fires both triggers. The `/api` build lands a private, 0%-traffic sha-tagged revision *and* flips the service's IAM to authenticated-only immediately. **The PWA build fails at Step 0 with `FATAL: trigger substitution … is empty`. That failure is designed, not a defect** — the substitutions are deliberately not set yet, and the guard exists precisely so that an empty `API_UPSTREAM_URL` cannot deploy a container that serves the PWA perfectly and silently 503s `/api`. Live traffic is unaffected throughout: it stays on the previous PWA revision, which carries no `/api` proxy at all, and no browser has ever called production `/api` directly.
4. **Now set both PWA trigger substitutions.** On the PWA trigger (`filename = app/cloudbuild.yaml`), set:
   - `_API_UPSTREAM_URL` — **read it, do not recall it or copy it out of a console listing:**
     `gcloud run services describe theygrow-api --region europe-west1 --format='value(status.url)'`.
     This is load-bearing, not a convenience. **The service answers on more than one URL** — Cloud Run publishes both a deterministic per-project hostname and a legacy hash-based one, and a per-revision `sha-` tagged URL on top of them. They all reach the service; they are **not** interchangeable here, because the same string is simultaneously the `proxy_pass` target and the ID-token `audience`, and Cloud Run rejects a token whose `aud` is not exactly the URL being called. `status.url` is the one the service considers its own, so it is the only correct source. It must be the **base service URL**, with no path and no trailing slash. A mismatch does not fail at build time or at container start — it fails as a `403` on every proxied request, which reads exactly like a missing `run.invoker` binding.
   - `_PWA_RUNTIME_SA` — the account from step 1.
5. **Re-run the PWA build.** It lands a 0%-traffic sha-tagged revision carrying the proxy. Live traffic is still on the previous revision and stays there until step 7.
6. **Smoke the tagged PWA revision** — get `$TAG_URL` exactly as in **Promotion + rollback (L1 deploy-safety gate)** step 2, then run the four assertions. This is the **only** real proof the packet works: the metadata server does not exist off Cloud Run, so nothing in CI or on a laptop can validate the token exchange, the audience match, or the IAM decision.
   - Proxied health: `curl -fsS "$TAG_URL/api/health"` → `{"status":"ok","service":"theygrow-api"}`. Anonymous — the *browser* sends no credential; the token is attached inside the container.
   - The container's own check still answers: `curl -fsS "$TAG_URL/health"` → `healthy`. This is the check that `^~ /api/` did not shadow the PWA's own `/health`.
   - The negative half, verified rather than assumed: `curl -s -o /dev/null -w '%{http_code}\n' "<prod /api base URL>/api/health"` → `403`. If this returns `200`, the service is still anonymously invocable and the packet has not taken effect — do not promote.
   - No CORS: `curl -sI "$TAG_URL/api/health" | grep -i access-control` → no output (grep exits 1).
   If the first assertion returns `403`, the `run.invoker` binding from step 2 is missing or names the wrong account. If it returns `503`, `_API_UPSTREAM_URL` was empty at build time — you smoked the step-3 revision instead of the step-5 one.
7. **Promote** the smoked PWA revision per **Promotion + rollback (L1 deploy-safety gate)** steps 4–5, and the `/api` revision per **Promotion + rollback (`/api`)** step 6.

**Rollback.** Withholding promotion is the abort: the previous PWA revision has no `/api` proxy and the previous `/api` revision keeps serving. Note the asymmetry — `--no-allow-unauthenticated` is **not** rolled back by traffic pinning, because it is service-level IAM. To restore anonymous access deliberately: `gcloud run services add-iam-policy-binding theygrow-api --member allUsers --role roles/run.invoker --region europe-west1` (and the next `/api` deploy will remove it again while the build-config carries the flag).

**Two honesty notes.**
- **The container fails closed.** If the upstream is configured but no ID token can be minted after its retry budget, `app/docker-entrypoint.sh` exits non-zero and the container never starts — a red Cloud Build rather than a revision that starts and 503s its way to promotion. A revision that fails to start takes zero users, because the deploy is `--no-traffic`.
- **There is no `resolver` in `app/nginx.conf`, deliberately.** The upstream hostname is resolved **once**, at config load. A change to the upstream's address is therefore picked up only on a new revision or a container restart, not live. Accepted as a residual risk for a stable Cloud Run service URL (`A3-DL-001`); the fix would be an `http`-level directive that the delivery-contract drift guard cannot see (`A1-DL-008`).

## Production database enablement (A3-P2, owner-run)

> **Owner GCP action.** Every `gcloud` command, console step and SQL statement below is run by the owner against the live project — Claude Code does not run `gcloud`, does not run SQL, and does not touch GCP. The production `/api` Cloud Run service `theygrow-api` and region `europe-west1` are live-infra identifiers carried in this RUNBOOK (see "Live-infra divergence"); the contract files do not name them. This section creates the **first** Cloud SQL instance in this project — there was none before it, and no Secret Manager secret, no VPC connector and no environment on `theygrow-api`.

What A3-P2 changed, in one paragraph: `api/cloudbuild.yaml` now deploys with `--add-cloudsql-instances`, `--set-secrets DATABASE_URL`, a dedicated `--service-account` and `--max-instances 2`, all behind a Step 0 guard; and `GET /api/health/ready` is the first deployed route that constructs `Settings` and opens a connection. `GET /api/health` is unchanged and stays environment-free.

**The steps below are strictly ordered. Steps 1–7 happen BEFORE the packet is merged; the trigger substitutions (step 9) happen AFTER.** That is the **same** ordering rule **Same-origin `/api` proxy** above carries, and the reason is Cloud Build's `MUST_MATCH` substitution option: a trigger that supplies a key the build-config on `main` does not declare fails **every** build until the packet lands. Setting the substitutions early breaks `main`.

1. **Create the Cloud SQL instance** (vault ADR-039 — these parameters are decided, not defaults to revisit): PostgreSQL **16**; region **europe-west1**; **Enterprise** edition; **zonal**, not HA; **public IPv4** with an **EMPTY authorized-networks list**; automated **daily backups** *and* **point-in-time recovery**.
   - **PITR must be on at creation.** It cannot be turned on retroactively for a window that has already passed, and the family diary has no source to rebuild from — there is no re-import that recovers it. This is the single most consequential checkbox in this section.
   - **The authorized-networks list stays empty. Permanently.** That is a load-bearing property, not a setting: with public IP and no authorized networks, the only two ways in are the Cloud SQL Auth Proxy (workstation) and the `--add-cloudsql-instances` Unix socket (Cloud Run), both IAM-authenticated. **One temporary `0.0.0.0/0` — even "just for five minutes to test something" — voids the entire posture**, because the instance is reachable from the internet the moment it exists. Private IP was explicitly rejected (ADR-039) to avoid a VPC layer and keep the owner-run procedures workable; an empty allowlist is what pays for that choice.
   - Record the instance id and instance connection name under "Live-infra divergence".
2. **Create the production database** on that instance, and record its name under "Live-infra divergence".
3. **`CREATE EXTENSION IF NOT EXISTS vector;` in that database, as the `postgres` superuser — before any migration.** Extensions are **per-database**, and here there is nowhere for one to carry over *from*: this is the first database on a brand-new instance. Migration `0001` runs the same statement, which then short-circuits without a privilege check — which is precisely what lets the application role in step 4 stay unprivileged. Skip this and you get a false choice: either the migration fails at revision `0001`, or the application role is a superuser and every barrier below is fiction.
4. **Create the application role with SQL — not with `gcloud sql users create`.** The gcloud/console path grants `cloudsqlsuperuser`, which carries `CREATEROLE` and `SET ROLE`. As `postgres`:
   `CREATE ROLE <app_role> LOGIN PASSWORD '<...>' NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT CONNECTION LIMIT 10;`
   then, so `alembic` can create tables without a superuser:
   `ALTER DATABASE <prod_db> OWNER TO <app_role>;` and `REVOKE ALL ON DATABASE <prod_db> FROM PUBLIC;`
   (On PostgreSQL 16 `PUBLIC` already has no `CREATE` on schema `public`, so the extra revoke the staging procedure branches on is not needed here.)
   **The `CONNECTION LIMIT` is arithmetic, not tidiness.** `db_pool_size` (2, `api/theygrow_api/parameters.py`) x `--max-instances` (2, `api/cloudbuild.yaml`) = **4** connections from the deployed service, hard-capped because `db_max_overflow` is `0`. A limit of **10** leaves **6** for your Auth Proxy sessions, `alembic` runs and `psql`. **Raise the role's `CONNECTION LIMIT` BEFORE raising `--max-instances`, never after** — the reverse order is how a deploy locks you out of your own database mid-incident.
5. **Create the Secret Manager secret holding the production `DATABASE_URL`.** Two URL forms exist and they are **not** interchangeable — **only the first goes into the secret**; the second is typed into your own shell for step 12 and is never stored anywhere:
   - **For Cloud Run — this is the secret's value** (`--add-cloudsql-instances` mounts the Cloud SQL Auth proxy as a **Unix socket** at `/cloudsql/<INSTANCE_CONNECTION_NAME>`; there is no TCP host):
     `postgresql+psycopg://<user>:<pass>@/<prod_db>?host=/cloudsql/<INSTANCE_CONNECTION_NAME>`
     Note the **empty authority** (`@/`). `theygrow_api.db.engine.engine_url()` normalizes via `make_url(...).set(drivername=...)`, which preserves the query dict, so `host=` reaches libpq as a socket directory. The variant some Cloud SQL documentation shows — `...@/cloudsql/PROJ:REG:INST/dbname` — parses as host `/cloudsql/PROJ` and **will not work** here.
   - **For your `alembic` run only** (step 12), over the Cloud SQL Auth Proxy on localhost — an environment variable in a local shell, not a stored secret:
     `postgresql+psycopg://<user>:<pass>@127.0.0.1:5432/<prod_db>`
   **Never write a connection string, host, user or password into this repository or this file** — placeholders only, exactly as in **Restore / disaster recovery**.
6. **Create the production runtime service account** (`theygrow-api-runtime`) and grant it, least-privilege: `roles/cloudsql.client` (project) and `roles/secretmanager.secretAccessor` **on this secret only** — not project-wide.
   This account is **not optional and not deferrable**. The project today has exactly one identity: the default compute service account, carrying `roles/editor` and shared by Cloud Build and both runtimes. Granting `roles/cloudsql.client` to *that* would open the family database to every workload in the project (ADR-038 as amended). Record the account under "Live-infra divergence".
   **Named limitation — `roles/cloudsql.client` is project-scoped and cannot be bound to one instance.** There is no per-instance IAM binding for it, so this account can reach **every Cloud SQL instance the project will ever have**. That is acceptable *only* while exactly one instance exists, and it stops being acceptable the moment a second one appears — at which point the narrowing options are separate projects, or Cloud SQL IAM database authentication with per-database grants. **The next instance must not silently inherit this access.**
7. **Grant the Cloud Build service account `roles/iam.serviceAccountUser` on that runtime account**, or the deploy fails with `Permission 'iam.serviceaccounts.actAs' denied` — an error that names nothing useful:
   `gcloud iam service-accounts add-iam-policy-binding <api_runtime_sa> --member serviceAccount:<cloudbuild_sa> --role roles/iam.serviceAccountUser`.
   Both step 6 grants must land before any deploy: `--set-secrets` pre-checks access, and a non-interactive build fails rather than prompting.
8. **Merge the packet.** This fires the `/api` trigger, and **the build fails at Step 0 with `FATAL: trigger substitution ... is empty`. That failure is designed, not a defect.** It is the guard doing its job: an empty `--add-cloudsql-instances` parses to an **empty list**, so the deploy would otherwise **succeed** with no attachment at all — on a service whose `/api/health` needs no environment and would stay green. Live traffic is untouched throughout; the previous revision keeps serving.
9. **Now set the three substitutions** on the production `/api` trigger (`filename = api/cloudbuild.yaml`): `_CLOUDSQL_INSTANCE` (instance connection name, step 1), `_DB_SECRET_NAME` (step 5), `_API_RUNTIME_SA` (step 6).
10. **Re-run the build.** It lands a private, 0%-traffic `sha-`tagged revision — now attached, secret-injected, running as the dedicated account, and capped at 2 instances. **`--max-instances 2` is a change, not a default:** the live service ran with `maxScale 20`, so this narrows the ceiling **tenfold**. It is deliberate — it is the other half of step 4's connection arithmetic — but it is a real reduction in burst capacity and you should know you made it.
11. **Take an on-demand backup and record the three facts** — the standing pre-migration step (**Restore / disaster recovery → Before every migration**). It is mandatory even here, on a database that is still empty: the habit is what makes it reliable later, and the recorded `alembic current` (`None`, at this point) and UTC start time are what a targeted restore needs. `gcloud sql backups create --instance <instance>`, then `gcloud sql backups list --instance <instance>` for the id.
12. **Run the migrations.** From `api/` — `alembic.ini` uses `script_location = alembic` with `prepend_sys_path = .`, so the working directory matters — with the Cloud SQL Auth Proxy running and `DATABASE_URL` set to the **TCP** form from step 5: `alembic upgrade head`. This brings the new database to the existing head (`0003`); A3-P2 adds **no** new revision. `api/alembic/` is **not** in the image (`api/Dockerfile` copies only `pyproject.toml` and `theygrow_api`), so migrations cannot be run from the deployed container — this is the workstation path. **Never run `alembic ... --sql` against production into a shared terminal or log**: offline mode renders the URL with `hide_password=False`.
13. **Smoke the tagged revision.** Get `$TAG_URL` exactly as in **Promotion + rollback (`/api`)** step 3. The service is private, so both calls need an identity token.
    - Liveness, unchanged and expected to stay unchanged: `curl -fsS -H "Authorization: Bearer $(gcloud auth print-identity-token)" "$TAG_URL/api/health"` → `{"status":"ok","service":"theygrow-api"}`.
    - Readiness: same command against `"$TAG_URL/api/health/ready"` → `200` `{"status":"ready"}`.
    **This is the first exercise of the socket URL form anywhere.** Nothing in CI, nothing on a laptop and no other contour has ever opened that path — CI's pgvector service proves the route and pool mechanics over TCP and nothing about the socket, the secret's contents, the attachment or the IAM decision. There is no staging contour to rehearse it on; there is no staging service at all.
    **A `503` here is the packet not working, and the body will not tell you why — by design.** It carries a fixed status enum and nothing else: no host, no user, no DSN, no driver text, no exception text. The diagnosis is in Cloud Logging, in the `readiness.probe` log line's bounded `failure_class`:
    - `config_invalid` — `DATABASE_URL` is absent or unparseable. The secret did not inject, or its value is malformed.
    - `connect_failed` — the URL parsed but the dial failed. Suspect, in order: the `@/` empty-authority form (the `...@/cloudsql/PROJ...` variant parses as a host and fails exactly here), a wrong `_CLOUDSQL_INSTANCE`, a missing `--add-cloudsql-instances`, or the role's password.
    - `query_failed` — connected, but `SELECT 1` failed. The role is at its `CONNECTION LIMIT`, or the database name is wrong.
14. **Promote** the revision you actually smoked, per **Promotion + rollback (`/api`)** step 6 (pinned revision, not `--to-latest`).
15. **Rollback, and what it does *not* undo.** Withholding promotion is the abort. Pinning traffic back to an earlier revision restores a revision with **no Cloud SQL attachment and no `DATABASE_URL`** — its `/api/health/ready` will answer `503` (or `404`, on a pre-A3-P2 image) while `/api/health` keeps answering `200`. That asymmetry is the point of keeping liveness environment-free. Traffic pinning does **not** undo: the Secret Manager secret, the two IAM grants on the runtime account, the Cloud Build `actAs` grant, or the Cloud SQL instance. Those are separate, deliberate deletions if you ever want them gone.

## Staging contour (L2, owner-run)

> **Owner GCP action.** Every `gcloud` command, console step and SQL statement below is run by the owner against the live project — Claude Code does not run `gcloud`, does not run SQL, and does not touch GCP. This section is a stop-gate handoff: the repository carries the build-config, this file carries the procedure, and neither carries a live identifier or a credential.

> **Nothing in this section has been raised.** Read the whole section as a procedure to execute, never as a description of something running. What exists is exactly two things: the build-config `api/cloudbuild.staging.yaml`, committed in A2-P1, and this procedure. What does **not** exist: the staging Cloud Run service, its Cloud Build trigger, the staging database, the staging role, the staging `DATABASE_URL` secret, the staging runtime service account, the seed run and the eval run. Nothing has been created and nothing has been deleted — the contour has simply never been stood up.
>
> **Its instance does not exist yet either.** Every "the Cloud SQL instance" reference below points at the production instance that **Production database enablement** above creates; that procedure is likewise committed and not yet executed, so there is no instance today. Per ADR-039 **one instance serves all contours**, so when both exist the staging database and role live inside the production instance rather than in a second one. Sequence follows from that: production database enablement first, this section after it.



**Staging never contains real family or child data** (ADR-020 / ADR-011 / ADR-014). Its database is seeded from a synthetic corpus only (A2-P2) and evaluated by the labeled query set (A2-P3). No third-party provider is cleared for staging: `embedder_privacy_cleared` and `answers_privacy_cleared` stay unset, so both egress gates are fail-closed and the contour makes zero provider calls. Since A2-P3 those gates are scoped to **egress** — an in-perimeter provider skips them because it crosses no third-party boundary, while anything that does not structurally declare zero egress stays gated exactly as before. That narrowing granted no clearance: **`answers_privacy_cleared` for the real answers LLM is still an open owner prerequisite**, ahead of the chat milestone. Any step where real data could reach staging is a stop-and-escalate, not a judgement call.

Canonical names to create: Cloud Run service **`theygrow-api-staging`**, database **`theygrow_staging`** on the production Cloud SQL instance, once **Production database enablement** has created it. The instance id / instance connection name / production database name are **not recorded in this repo** (see "Live-infra divergence") — read them from the console as you go.

1. **Create the staging database.** `theygrow_staging`, on the production instance. One instance for all contours is the ADR-039 rule and the accepted ADR-020 cost default; steps 3–4 are what make this an isolated contour rather than a shared one.
2. **Pre-create the `vector` extension as the superuser — before any migration.** Migration `0001` runs `CREATE EXTENSION IF NOT EXISTS vector`, which on Cloud SQL requires membership in `cloudsqlsuperuser`. Extensions are **per-database**, so production's does not carry over to the new one. Connected to `theygrow_staging` as the `postgres` superuser: `CREATE EXTENSION IF NOT EXISTS vector;`. Afterwards `IF NOT EXISTS` short-circuits without a privilege check, so an unprivileged role can run the migrations in step 8. Skip this and you get the false choice the rest of this section exists to avoid: either the migration fails at revision `0001`, or the staging role is a superuser and the isolation barrier below is fiction.
3. **Create the staging role with SQL — not with `gcloud sql users create`.** The gcloud/console path grants `cloudsqlsuperuser`, which carries `CREATEROLE` and can `SET ROLE` to other members, including whatever role owns the production database. That single convenience voids the whole barrier, at the step an operator is most likely to take without thinking. Instead, as `postgres`:
   `CREATE ROLE <staging_app_role> LOGIN PASSWORD '<...>' NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT CONNECTION LIMIT 8;`
   The connection limit is **production safety, not tidiness**: staging and production share one instance's `max_connections`, so a runaway staging client can lock production out. It pairs with `--max-instances 2` on the staging service.
4. **Make the barrier real, then verify it.** In order:
   - **Pre-check first, and do not skip it:** confirm the production application role holds an **explicit** `GRANT CONNECT` on the production database (`\l` or `SELECT datacl FROM pg_database WHERE datname = '<prod_db>';`). The next command removes `PUBLIC`'s implicit grant, and any production principal relying on that implicit grant instead of an explicit one will lose access.
   - Connected to the **production** database as `postgres`: `REVOKE CONNECT ON DATABASE <prod_db> FROM PUBLIC;`. PostgreSQL grants `CONNECT` to `PUBLIC` on every database by default (inherited from `template1`) — without this revoke the staging role can connect to production and read the entire catalogue: every schema, table and column name. This is the one step in this handoff that mutates the **production** database; it is reversible with a matching `GRANT`.
   - Check the major version (`SELECT version();`). On PostgreSQL **< 15**, `PUBLIC` also retains `CREATE` on schema `public`, so a connected role could create objects inside the production database: `REVOKE CREATE ON SCHEMA public FROM PUBLIC;` in the production database as well. On 15+ this default is already gone.
   - Symmetry on the staging side: `ALTER DATABASE theygrow_staging OWNER TO <staging_app_role>;` and `REVOKE ALL ON DATABASE theygrow_staging FROM PUBLIC;`.
   - **Verify the negative — do not assume it.** Connect as `<staging_app_role>` to the **production** database name and confirm the connection is **refused**. Nothing in the repository can check this, and no test covers it; an observed refusal is the only thing that turns "no grant on production" from a claim into a fact. Record that you ran it.
5. **Create the Secret Manager secret holding the staging `DATABASE_URL`.** Two URL forms exist and they are **not** interchangeable — **only the first goes into the secret**; the second is typed into the owner's own shell for step 8 and is never stored anywhere:
   - **For Cloud Run — this is the secret's value** (`--add-cloudsql-instances` mounts the Cloud SQL Auth proxy as a **Unix socket** at `/cloudsql/<INSTANCE_CONNECTION_NAME>`; there is no TCP host):
     `postgresql+psycopg://<user>:<pass>@/theygrow_staging?host=/cloudsql/<INSTANCE_CONNECTION_NAME>`
     Note the **empty authority** (`@/`). `theygrow_api.db.engine.engine_url()` normalizes via `make_url(...).set(drivername=...)`, which preserves the query dict, so `host=` reaches libpq as a socket directory. The variant some Cloud SQL documentation shows — `…@/cloudsql/PROJ:REG:INST/dbname` — parses as host `/cloudsql/PROJ` and **will not work** here.
   - **For the owner's `alembic` run only** (step 8), over the Cloud SQL Auth Proxy on localhost — environment variable in a local shell, not a stored secret:
     `postgresql+psycopg://<user>:<pass>@127.0.0.1:5432/theygrow_staging`
   **Never write a connection string, host, user or password into this repository or this file** — placeholders only, exactly as in **Restore / disaster recovery**.
6. **Create the runtime service account and grant it, least-privilege:** `roles/cloudsql.client` (project) and `roles/secretmanager.secretAccessor` **on the staging secret only** — not project-wide, or staging can read production's secrets. Then grant the **Cloud Build** service account `roles/iam.serviceAccountUser` **on that runtime service account**: without this `actAs` grant the very first staging deploy fails with `Permission 'iam.serviceaccounts.actAs' denied`. Both grants must land **before** step 7, because `--set-secrets` pre-checks access and a non-interactive build fails rather than prompting.
7. **Create the staging trigger, and amend the production one.**
   - Staging: push to `main`, `filename = api/cloudbuild.staging.yaml`, `includedFiles = api/**`, `ignoredFiles = api/cloudbuild.yaml`. Set the three substitutions from the console values: `_CLOUDSQL_INSTANCE` (instance connection name), `_DB_SECRET_NAME` (step 5), `_STAGING_RUNTIME_SA` (step 6).
   - Production: add `ignoredFiles = api/cloudbuild.staging.yaml`. Without the reciprocal filters, editing either build-config rebuilds and re-tags **both** services.
   - If a substitution is missing or empty the build fails at step 0 with a named message. That guard exists because the silent failure is worse than the loud one: an empty `--add-cloudsql-instances` parses to an empty list, so the deploy **succeeds** with no database attachment and `/api/health` stays green.
8. **Run the migrations against staging.** From `api/` — `alembic.ini` uses `script_location = alembic` with `prepend_sys_path = .`, so the working directory matters — with the Cloud SQL Auth Proxy running and `DATABASE_URL` set to the **TCP** form from step 5: `alembic upgrade head`. Note that `api/alembic/` is **not in the image** (`api/Dockerfile` copies only `pyproject.toml` and `theygrow_api`), so migrations cannot be run from the deployed container; this is the workstation path, and it is the same path the standing pre-migration backup step targets. **Never run `alembic … --sql` against staging into a shared terminal or log** — offline mode renders the URL with `hide_password=False`.
9. **Smoke the staging service.** It is private, so a bare `curl` returns 403. Either:
   `curl -fsS -H "Authorization: Bearer $(gcloud auth print-identity-token)" "$STAGING_URL/api/health"` → `{"status":"ok","service":"theygrow-api"}` (the caller needs `roles/run.invoker`), or `gcloud run services proxy theygrow-api-staging --region europe-west1` and curl the local address.
10. **Staging rollback.** Staging deploys at 100% traffic with no gate, so a bad deploy takes staging down and the only recovery is to pin the previous revision:
    `gcloud run services update-traffic theygrow-api-staging --to-revisions <prev-revision>=100 --region europe-west1`.
11. **Seed the staging database from the synthetic corpus (A2-P2).** Same workstation path as step 8 — Cloud SQL Auth Proxy running, `DATABASE_URL` set to the **TCP** form, run after `alembic upgrade head` because the seed writes rows and does not create tables. From the repository root:
    `theygrow-seed-staging --corpus api/corpus/staging`
    The corpus is **not** in the image (`api/Dockerfile` copies only `pyproject.toml` and `theygrow_api`, and `api/.dockerignore` lists `corpus/`), so this runs from a checkout — which is why `--corpus` is required and has no default. Expect `exports=3 inserted=136 quarantined=0 sources=136`; counts only, never diary text. Re-running is safe: the seed is idempotent and converges rather than duplicating.
    Three properties worth knowing before you run it, because they are what make this step safe to hand to an operator:
    - **It refuses on the wrong database, twice.** The database name in `DATABASE_URL` is checked before any connection is opened, and `SELECT current_database()` is checked on the connected server before any write. Both must equal `theygrow_staging`; a production name, a near-miss and a missing name all refuse. Pasting production's URL here is a loud no-op, not a disaster (`L2-P2-INV-001`).
    - **It makes zero third-party calls.** Embeddings are computed in-perimeter, so `embedder_privacy_cleared` and `answers_privacy_cleared` stay unset and no provider is contacted or billed. If a run ever asks for a clearance flag, stop — something is injecting the real embedder.
    - **It is one transaction.** A failure anywhere — malformed export, missing table — leaves staging exactly as it was.
    **The corpus is invented.** It contains no real family or child data and is not derived from production (`api/corpus/staging/README.md`). No test can prove that; if you ever add to the corpus, that rule binds the addition.
12. **Run the eval against staging (A2-P3).** This is the step the `/api` promotion gate above names as its precondition. Same workstation path as steps 8 and 11 — Cloud SQL Auth Proxy running, `DATABASE_URL` set to the **TCP** form — and it must run **after** step 11, because it refuses an unseeded contour rather than reporting a vacuous pass. From the repository root, with an identity token for the private staging service in the environment (the same token step 9 uses; the command never runs `gcloud` itself):
    `THEYGROW_EVAL_IDENTITY_TOKEN="$(gcloud auth print-identity-token)" theygrow-eval --mode staging --corpus api/corpus/staging --health-url "$STAGING_URL/api/health" --out eval-scorecard.json`
    Exit `0` = every labeled case met its recorded expectation. Exit `1` = a contract-conformance regression; the scorecard's `failures` array names the case ids and which checks failed. Exit `2` = the run could not happen at all (wrong database, unseeded contour, stored vectors disagreeing with the corpus lexicon, staging not answering) — **exit 2 is not a pass and not a failure, it means the gate never ran.** Drop `--mode staging` and the two flags that go with it to check the database alone without the liveness assertion.
    Four things to know before you rely on it:
    - **It refuses the wrong database, twice, exactly as the seed does** — even though it only reads. The seed's guard protects writes; this one protects the artifact, whose counts would otherwise describe whatever database it happened to reach.
    - **It makes zero third-party calls.** Both providers are in-perimeter, so `embedder_privacy_cleared` and `answers_privacy_cleared` stay unset and the run is free and repeatable. If a run ever asks for a clearance flag, stop — something is injecting a real provider.
    - **The liveness assertion proves ingress only.** It says the staging service is up and answering an authenticated request. It does **not** say the service can reach the database this eval reads — no deployed route opens a connection (see the first honesty note below). Both are checked because both are part of "staging is green"; neither stands in for the other.
    - **The scorecard is safe to paste anywhere.** Case ids, bounded check names, counts and timings only — no query text, no diary text, no chunk ids, no community id.

**Three honesty notes, so the contour is not trusted beyond what it proves.**

- **The database wiring is not exercised by the deployed service.** `/api/health` opens no connection, and this contour's service will carry no route that does: `GET /api/health/ready` arrived in A3-P2 on the **production** build-config only. `--set-secrets` validates only that the secret **exists** and that the runtime service account can **read** it — never that its contents are a usable URL, and never that the socket resolves. Until step 11's seed has actually been run, the only positive evidence the wiring is correct will be step 4's observed refusal and step 8's successful migration. Treat a green deploy as evidence of nothing here. Note that step 11 runs from a workstation over the proxy, so even a successful seed exercises the **TCP** URL, not the socket form the deployed service mounts. On production the readiness probe is what closes that gap (**Production database enablement**, step 13) — once that procedure has been run; here nothing closes it.
- **Staging validates the source tree at a commit, not the image production will run.** The two triggers run two independent `docker build`s of the same commit, and those are not guaranteed to be the same bits: `api/Dockerfile` pins the mutable `python:3.12-slim` tag, `api/pyproject.toml` uses `>=` ranges, and `api/uv.lock` is not used by the Dockerfile. Build-once-promote-the-digest is the fix and is deferred (`L2-DL-001`).
- **Staging is not a parity twin of production's ingress.** Both are private — production `/api` has carried `--no-allow-unauthenticated` in its build-config since A3-P1 — but they are reached differently: production sits behind the PWA's nginx and is invoked service-to-service by the PWA runtime account holding `roles/run.invoker`, while staging is called directly with an owner identity token and has no proxy in front of it. A green staging run therefore says nothing about the production proxy path, its token audience, or its IAM decision.

**Two shared-instance consequences to carry**, because per ADR-039 the staging database will live on the production instance once both exist: an in-place backup restore is **instance-wide** and would destroy `theygrow_staging` as collateral, and a PITR clone would clone both databases (see **Restore / disaster recovery**). And Cloud SQL storage auto-grows but **never shrinks** — running the A2-P2 synthetic seed permanently raises the instance's billed disk floor.

## KB artifact (owner-run sync + version bump)

> **Owner action.** The sync is owner-run, RUNBOOK-style — deliberately **not** wired into pre-commit/CI (`scripts/sync-kb-artifact.sh` header records the design). The app consumes the artifact **byte-as-published** (`VDK-P3-INV-001`): never hand-edit `app/kb-v{N}.json`; data fixes happen producer-side in `theygrow-domain-kb` and arrive as a new artifact version.

1. **Sync / re-vendor a version.** `scripts/sync-kb-artifact.sh <N> [kb-repo-url-or-path]` vendors `compiled/kb-v{N}.json` from the `theygrow-domain-kb` **release tag** `kb-v{N}` (vault ADR-026 §2 tag-anchor annotation) into `app/kb-v{N}.json`, byte-identical — never floating `main` (`compiled/` holds only the current version, so the tag is the only reproducible anchor for a frozen version). Idempotent: a re-run overwrites with identical bytes. The script verifies the artifact exists in the tag and `"kb_version"` equals the filename `N`; deeper schema validation stays producer-side.
2. **Bump to a new artifact version (new `kb-v{N}.json`)** — the full consumer-side checklist (each step is required; the nginx location `^/kb-v[0-9]+\.json$` and the sync script are N-generic and need no change):
   1. Run the sync for the new `N` (step 1) — lands `app/kb-v{N}.json`.
   2. `app/index.html` — update the fetch-URL literal (`kbReady = fetch('/kb-v{N}.json')`); filename-versioning, not a runtime knob.
   3. `app/sw.js` — replace the `OFFLINE_URLS` entry with `'/kb-v{N}.json'`.
   4. `app/Dockerfile` — update the `COPY kb-v{N}.json` line.
   5. `app/sw.js` — bump `CACHE_VERSION` (delivers the new shell + artifact to installed users via the network-first SW + `#updateBanner` path, `PWA-DL-001`; `activate()` purges the old cache with the old artifact).
   6. `.pre-commit-config.yaml` — update the excluded filename (`kb-v{N}\.json`) in **both** rewriting-hook excludes (`trailing-whitespace`, `end-of-file-fixer`) so the new artifact stays byte-as-published.
   7. Decide the old `app/kb-v{M}.json`'s fate in the same packet (owner call at bump time — the app references exactly one version, and the old bytes stay reproducible via the domain-kb tag `kb-v{M}`, so retiring it is the natural default; no policy is pre-fixed here).
3. **Promotion.** The no-traffic revision smoke (step 3 of **Promotion + rollback (L1 deploy-safety gate)** above) includes the two kb checks — immutable `Cache-Control` and served-sha256 == vendored.

## Module mount (owner-run version bump)

> **Why this section exists.** `/m/v{N}/` is served `public, immutable, max-age=2592000` at a URL that carries no content hash. **A `CACHE_VERSION` bump alone does NOT deliver changed bytes at an existing mount URL** — `cache.addAll` goes through the HTTP cache, so inside the 30-day immutable window the browser hands the new worker its stored copy without revalidating, and the new cache generation is filled with the **stale** file. It then survives every subsequent bump. Changing the bytes at a published mount URL is therefore not a thing this project does. See `A1-DL-004`.

1. **When to bump.** Any change to the bytes of a file under a published mount version — a one-character CSS fix included. The mount version is a content generation, not a semver: it carries no meaning beyond "these bytes are not those bytes".
2. **Bump to a new mount version (`/m/v{N+1}/`)** — copy-forward, never rename:
   1. `cp -r app/m/v{N} app/m/v{N+1}`, then make the change **in the new directory only**. `app/m/v{N}/` stays on disk **byte-untouched** so any client holding cached HTML that references it keeps resolving it for the cache lifetime (vault ADR-024: a published immutable asset is never rewritten or removed in place — the `ICON-DL-001` / `A0-DL-001` precedent for superseded icon filenames).
   2. `app/index.html` — repoint every `/m/v{N}/…` reference at `v{N+1}`. Since A1-P6 that is ~18 references, not three: the stylesheet `<link>`, the two `<script type="module" src>` entries, **and the fifteen `<link rel="modulepreload">` hints**. A missed hint is not a functional break — it is a cross-version fetch of bytes nothing evaluates, plus the round trip the hint was meant to remove — and `A1-P6-INV-001` fails on it by name.
   3. `app/sw.js` — repoint **every** `/m/v{N}/…` entry in `OFFLINE_URLS`. Since A1-P4 that list covers the whole module graph (`app.js` plus each file under `core/` and, since A1-P5, under `surfaces/`), not just the two files the shell names — `cache.addAll` is atomic and an unrepointed entry fails the install outright.
   4. `app/sw.js` — bump `CACHE_VERSION` (delivers the new shell to installed users via the network-first SW + `#updateBanner` path, `PWA-DL-001`; `activate()` purges the old generation). Required for the precache to be re-filled from the *new* URLs — not, on its own, sufficient to refresh an *existing* URL (see above).
   5. **No `app/Dockerfile` change.** `COPY m/ /usr/share/nginx/html/m/` ships the whole mount root, so a new version directory ships automatically — the one step the KB-artifact checklist above requires that this scheme eliminates. Likewise no `app/nginx.conf` change (the generic static location is version-agnostic) and no `.pre-commit-config.yaml` change (the exclude is the version-agnostic `m/` prefix).
   6. The ship-list guard (`app/tests/delivery-contract.spec.js`) fails if steps 2 and 3 disagree, or if either points at something the image does not ship. Run the parity suite before promoting.
3. **Retiring an old mount version** is a **separate owner cleanup**, never part of the bump packet — the same posture as the orphaned icon placeholders (vault ADR-024 OQ#1). A version may be dropped once no cached HTML can still reference it; the shell's own `max-age=3600, must-revalidate` bounds that window in practice, but the call stays the owner's.
4. **Promotion.** The no-traffic revision smoke (step 3 of **Promotion + rollback (L1 deploy-safety gate)** above) includes the mount's immutable `Cache-Control` and `Content-Type` checks.

## Restore / disaster recovery

The production episodic store is **managed Cloud SQL PostgreSQL + pgvector** (ADR-008). This section is the recovery path for it: point-in-time restore → stand up → validate → switch the connection → return traffic → review. It is written to be executable end-to-end from this document alone, under stress, without reading anything else.

**The likelier disaster here is logical, not physical.** Cloud SQL manages the hardware; what this project can do to itself is a bad Alembic migration or a bad backfill run — schema and data damage that replicates faithfully into every backup taken after it. Migrations are run **by hand** against the target database (there is no deploy-time release step: `api/cloudbuild.yaml` carries no migration step and no `scripts/` runner exists), so the pre-migration backup below is the single most load-bearing habit in this section.

> **Owner GCP action.** Every `gcloud` command and console step below is run by the owner against the live project — Claude Code does not run `gcloud` and does not touch GCP. The Cloud SQL identifiers are **not recorded in this repo yet** (see "Live-infra divergence"); read them from the console before starting and substitute them for `<instance>` throughout.

### Targets (adopted, `A1-DL-003`)

- **RPO — 5–15 minutes**, *conditional on PITR being enabled on the live instance.* Cloud SQL point-in-time recovery replays archived write-ahead logs, which is what buys minutes instead of hours. This repo carries **no** infrastructure-as-code and no Cloud SQL configuration of any kind, so PITR status is **not derivable here — verify it, do not assume it**: `gcloud sql instances describe <instance> --format 'value(settings.backupConfiguration)'` (look for point-in-time recovery enabled, plus the transaction-log retention). **If PITR is off, the real RPO is the age of the last automated backup — up to 24 hours, not 5–15 minutes.** Discovering that mid-incident is the failure mode this line exists to prevent.
- **Retention window.** PITR reaches back only as far as transaction-log retention (Cloud SQL default: 7 days; configurable 1–35). A recovery point outside the window is unreachable at any price, and the newest automated backup taken before the damage becomes the only anchor. Read the live value from the same `describe` output, and record it here once known.
- **RTO — 2–4 hours**, with the caveat that matters more than the number: **an untested RTO is an assumption, not an RTO.** No restore drill has been run on this project. Until one has been run end-to-end and timed (see **Drill cadence** below), treat 2–4 h as a target, not a commitment, and do not quote it as a guarantee.

### Before every migration (standing pre-step)

Migrations are run manually — `alembic upgrade head` from `api/` with `DATABASE_URL` pointed at the target database. Three revisions have landed (`0001` `source_messages`; `0002` `notes` + `event_chunks`; `0003` per-chunk `vector(1536)` embedding). Before every such run against production:

1. **Take an on-demand backup and keep its id.** `gcloud sql backups create --instance <instance>`, then `gcloud sql backups list --instance <instance>` to capture the id.
2. **Record the from-revision.** `alembic current` (from `api/`, `DATABASE_URL` set) — the revision you are upgrading *from* is the one you will want back.
3. **Record the wall-clock start time (UTC).** PITR takes a timestamp, not a revision; the moment immediately before the migration started is the recovery point for step 1 below.

Those three facts — backup id, from-revision, start timestamp — are what a targeted restore needs. Taking the backup and not writing down the timestamp discards most of its value.

### Restore procedure

1. **Stop the writers, then pick the recovery point.**
   - Today the only processes that **write** to the store are the owner-run offline CLIs (`theygrow-import-export`, `theygrow-rederive`, `theygrow-embed`) — stop them. Since A3-P2 the production `/api` service *does* connect, but only to `SELECT 1` from `GET /api/health/ready`: it is a reader, it writes nothing, and it holds at most `db_pool_size` x `--max-instances` = 4 connections. It therefore does not need to be cut to make a restore safe — but withhold or roll back its traffic anyway if the restore window matters, because a probe against a half-restored instance is a misleading green. The moment a *writing* route lands, cutting traffic first (**Promotion + rollback (`/api`)** above) stops being optional.
   - Pick the target timestamp (UTC, RFC 3339). For a bad migration it is the moment immediately **before** the migration started (recorded in the pre-step above); for corruption found later, the last moment the data can be positively asserted good. Round *earlier*, never later — losing ten good minutes beats restoring ten poisoned ones.
   - Confirm the timestamp falls inside the retention window. If it does not, the newest automated backup taken before the damage is the only remaining option (`gcloud sql backups list --instance <instance>`, then `gcloud sql backups restore <backup-id> --restore-instance <instance>`) — and the RPO for this incident is whatever that backup's age turns out to be. **That restore is instance-wide.** Per ADR-039 one instance serves all contours, so once a staging contour is raised the same instance also hosts `theygrow_staging`, which an in-place restore destroys as collateral. Staging holds synthetic data only, so that costs a re-seed and not an incident — but find it out here, not afterwards. No staging database exists today (**Staging contour**), so today the restore touches the production database alone; check what is actually on the instance rather than trusting this sentence.
2. **PITR restore into a NEW instance** (owner). Cloud SQL point-in-time recovery **clones**; it never rewinds in place: `gcloud sql instances clone <instance> <restored-instance> --point-in-time <RFC3339-UTC>`. That is useful, not a limitation — the damaged instance stays untouched as evidence and as the fallback if the chosen recovery point proves wrong. Name the clone so it is obviously temporary and dated. This clone is the long pole in the RTO budget. The clone carries **every** database on the instance, so once a staging contour is raised it also carries a copy of `theygrow_staging` — harmless (synthetic data), but one more thing to delete with the temporary instance. No staging database exists today, so today the clone carries the production database alone.
3. **Stand up the restored instance** (owner).
   - Wait for `RUNNABLE`: `gcloud sql instances describe <restored-instance> --format 'value(state)'`.
   - The clone inherits region, tier, flags and databases from the source — confirm rather than assume, the region especially (a cross-region clone adds latency to every subsequent query).
   - Confirm the extension: `SELECT extname, extversion FROM pg_extension;` → `vector` must be listed (ADR-008; migration `0001` also creates it).
   - Confirm the application role can connect. A clone carries its users, but a restore that lands with no usable login burns the switch window.
4. **Validate BEFORE switching anything.** Three tiers, in this order — do not jump to the smoke test.
   1. **Migration state.** From `api/` with `DATABASE_URL` pointed at the restored instance: `alembic current` must equal the **intended** revision — after a bad-migration incident that is the from-revision recorded in the pre-step, *not* `head`. A restored database sitting at `head` after you restored to escape `head` means the recovery point was too late.
   2. **Structure and integrity.** Row counts per table against last-known-good — `source_messages`, `notes`, `event_chunks` — plus a check that `event_chunks.embedding` is populated where it should be and that the HNSW index on it survived. That index is built by the offline backfill *after* bulk population rather than by a migration, so it is the most plausible thing to go silently missing; retrieval still returns results without it, just slowly and without complaining. Where **physical** damage is suspected rather than logical, run a `pg_amcheck --heapallindexed`-class check against the restored instance before trusting it.
   3. **Application-level smoke.** Point a local process at the restored instance (`DATABASE_URL` in the environment — never in a file, never committed) and exercise a real read path through the offline retrieval CLI. Note what this is **not**: `pytest api` runs against an ephemeral CI database and proves nothing whatsoever about the restored data.
5. **Switch the connection** (owner, Cloud Run). The application's single connection knob is the environment variable `DATABASE_URL` — bound and validated by `theygrow_api.config.Settings`, normalized to the `postgresql+psycopg` driver in `theygrow_api.db.engine`. Switching means updating that variable, and the Cloud SQL attachment, on the Cloud Run service.
   - **Read the live state first:** `gcloud run services describe theygrow-api --region europe-west1`. Since A3-P2 `api/cloudbuild.yaml` — the **production** config — declares the Cloud SQL attachment and the `DATABASE_URL` secret, so the wiring **is** reproducible from this repo and a redeploy restores it. What that changes for a restore: switching the connection means pointing the **secret's value** at the restored instance and updating `_CLOUDSQL_INSTANCE` on the trigger, not hand-setting an environment variable on the service — and a redeploy from an unamended trigger will point the service straight back at the damaged instance. Amend the trigger *before* you redeploy.
   - **Never write the connection string into this repository or this file.** This file names the *variable* and the *location* (the Cloud Run service config, or a Secret Manager secret referenced by `--set-secrets`) — never a value, host, user or password.
   - Update the connection first and traffic second. They are two decisions; one command that does both removes the only chance to inspect.
6. **Return traffic** (owner). Use the existing promotion mechanics rather than a bespoke path: land the new configuration on a fresh revision at **0% traffic**, smoke it on its per-revision tagged URL, then shift traffic — the full procedure, rollback included, is **Promotion + rollback (`/api`)** above (the connection knob in step 5 is on the `/api` service, so that is the gate this step goes through). If the smoke fails, withholding promotion costs nothing; the previous revision is still serving.
7. **Erasure-suppression reconciliation — N/A until accounts.** A restore rewinds the database past deletions as well as past damage: any erasure a family requested between the recovery point and now is silently resurrected by step 2. Once accounts and deletion semantics exist (vault ADR-010 / PDR-010, arriving with the authenticated spine), re-applying every such erasure against the restored instance becomes a **mandatory** gate before step 6 returns traffic. Today there are no accounts, no deletion semantics and no suppression ledger, so this step is a **no-op** — it sits in the sequence now so that it is inherited rather than rediscovered.
8. **Post-incident review.** Same day, while it is still accurate:
   - **Time it honestly.** Wall-clock from detection to restored traffic is the achieved RTO; the gap between the recovery point and the last good write is the achieved RPO. Compare both against the targets above, and correct the targets if reality disagrees — a target no incident has ever met is a wish.
   - **Decide the damaged instance's fate deliberately** (keep it as evidence for a defined number of days, then delete), and prune the temporary restored/drill instances — they bill by the hour.
   - **Record it.** If the incident changes a target, a step or a habit here, that is a `docs/decision-log.md` entry, not a memory.

### Drill cadence (owner action)

- **After each migration — light drill.** PITR-clone to a throwaway instance at the pre-migration timestamp, run validations 4.1 and 4.2 against it, delete it. This proves the recovery point and the backup are real while finding out otherwise is still cheap.
- **Periodically — full drill.** Run the whole sequence through step 6 against a non-production target, and **time it**. This is the only thing that converts the 2–4 h RTO from an assumption into an RTO.

Neither drill is automated, and nothing in CI runs any part of this section.

### Future state — AlloyDB (not today)

Nothing in this repo targets AlloyDB; the production store is Cloud SQL (ADR-008 names AlloyDB as a by-load successor). If that migration happens the sequence above holds, but steps 2 and 3 change shape: AlloyDB point-in-time recovery restores to a **new cluster**, not a new instance, and a restored cluster has no serving endpoint until a **primary instance is created manually** inside it. The connection switch therefore becomes two-step (create the primary, then switch the connection string), and the RTO budget must absorb cluster-plus-instance provisioning rather than a single clone. Revisit this section deliberately when the store moves; do not improvise it during an incident.

## Local dev

The PWA is buildless — no bundler, no transpiler; the files execute as they lie. Since A1-P3 the shell loads assets out of `/m/v{N}/` by absolute URL, so it must be served over HTTP; opening `app/index.html` from the filesystem no longer works. Two minimal options:

- **Static server.** Serve the `app/` directory with any static file server (e.g. `python -m http.server 8080 --directory app`) and open `http://localhost:8080`.
- **Container parity.** Build and run the production container locally via `docker build -t theygrow-app app && docker run --rm -p 8080:8080 theygrow-app` (build context `app/`). This matches the production nginx config.

### Parity suite (`/app`) — the A1 spa-split gate

The three-level parity suite (DOM snapshot + visual regression + behavioural smoke) is the acceptance gate for every `spa-split` packet, and the repo's only frontend CI gate. It is dev/CI-only: it is excluded from the production image (`app/Dockerfile` COPYs an explicit file list) and from the Docker build context (`app/.dockerignore`), so the delivery channel stays buildless.

- **Run it**: `scripts/parity-suite.sh`. CI calls this same script, so the gate cannot drift into a local shadow of itself.
- **A subset**: `scripts/parity-suite.sh --project=behavior` (projects: `contract`, `dom-desktop`, `dom-mobile`, `behavior`, `visual-desktop`, `visual-mobile`).
- **Update baselines** — deliberate act, never implicit: `scripts/parity-suite.sh --update-snapshots`. `app/playwright.config.js` sets `updateSnapshots: 'none'`, so without this flag a missing or changed baseline **fails**. Review the resulting diff in `app/tests/__baselines__/` before committing; an unexplained baseline change is a product change.
- **Requires Docker.** The script runs the suite inside a pinned browser container. Without a Docker daemon: `sudo service docker start` (or the platform equivalent).

**Two pins hold the suite; change them only deliberately.**

1. **Version pin.** `@playwright/test` in `app/package.json` and `PLAYWRIGHT_VERSION` in `scripts/parity-suite.sh` must be the same exact version (currently **1.61.1**, image `mcr.microsoft.com/playwright:v1.61.1-noble`). The script refuses to run on a mismatch. Bumping either re-baselines every screenshot.
2. **Platform pin.** `setFixedSkillColumnWidth()` in `app/m/v1/surfaces/table.js` sizes the skill column from measured text, so screenshots are font-metric dependent. Visual baselines are valid **only** inside that container. `PARITY_NO_DOCKER=1 scripts/parity-suite.sh --project=dom-desktop --project=behavior` runs the non-visual projects on the host (host browsers need Chromium's system libraries: `npx playwright install --with-deps chromium`); visual projects run that way will legitimately mismatch.

**Time is pinned too.** The app derives age — and therefore the current-month column, ZPD readiness and the activities ranking — from `new Date()`. Every test freezes the clock (`app/tests/support/seed.js`), so baselines do not rot daily. A baseline diff that appears "just because time passed" means the pin broke, not that the app changed.

**Delivery drift guard.** `app/tests/server.js` mirrors `app/nginx.conf` so the suite can serve a `CACHE_VERSION`-mutated `/sw.js` on the same origin (the PWA update flow is untestable otherwise; `app/sw.js` on disk is never modified). `app/tests/delivery-contract.spec.js` parses the real `nginx.conf` and **fails when the two diverge** — so editing `nginx.conf` cache/MIME rules without updating the mirror reds the gate on purpose.

**Ship-list drift guard** (A1-P3, a second and different guard). The parity server serves from the `app/` directory **on disk**, so a file `app/Dockerfile` forgets to `COPY` passes the whole suite and 404s only in production — and `app/Dockerfile` has no wildcard `COPY`. `app/tests/delivery-contract.spec.js` therefore parses the real `COPY` list and asserts, in both directions, that everything the shipped shell references is shipped by the image *and* precached by name in `OFFLINE_URLS`. Since A1-P4 it asserts the same two things about a **third** surface — the transitive static `import` graph reached from the shell's `<script type="module">` entries (`A1-P4-INV-001`), which is the only thing standing between a new `core/` or `surfaces/` file and a production 404 that no other test can see. Since A1-P6 there is a **fourth** direction: the `<link rel="modulepreload">` hint set must equal that import graph exactly, in both directions (`A1-P6-INV-001`). That direction is also why the third is rooted where it is — hints are `href=` attributes, so seeding the walk from every `.js` the shell names would make it delete the whole graph as "entries" and assert nothing at all, silently (`A1-DL-007` (d)). The second direction is what keeps a copy-forward mount bump honest: both `/m/v1/` and `/m/v2/` stay shipped, so a shell pointing at `v2` while `OFFLINE_URLS` still lists `v1` would otherwise be invisible. The parser fails **closed** — any `COPY` form it does not fully understand throws rather than guessing. It does **not** consult `app/.dockerignore`: never add a pattern there matching `m/`.

### `/api` (FastAPI)

The `/api` service runs as a standalone ASGI app. In production it sits behind the PWA's nginx since A3-P1 (the same-origin proxy), but nothing about that is reproduced locally: run it directly, on its own port, and reach it directly.

- **Install** (the api-scoped PEP 621 package, with dev extras): `python -m pip install "./api[dev]"`.
- **Run**: `uvicorn theygrow_api.main:app --reload`. No environment is required to *start* it — application construction still builds no config and opens no connection. Since A3-P2 one route needs a database once called; see the note below.
- **Check**: `curl http://localhost:8000/api/health` → `{"status":"ok","service":"theygrow-api"}`.
- **Types / tests**: `mypy api` and `pytest api`.

The config module (`theygrow_api.config.Settings`) requires `DATABASE_URL` (no default) **when constructed**. Since A3-P2 exactly one route constructs it — `GET /api/health/ready`, and only lazily, on the first request that builds the served engine. `GET /api/health` still constructs no config and opens no connection, which is why the run instruction above needs no environment: without `DATABASE_URL`, liveness answers `200` and readiness answers `503 {"status":"unavailable"}`. Everything else that touches the database is still an offline CLI (`theygrow-import-export`, `theygrow-rederive`, `theygrow-embed`), run out-of-band with `DATABASE_URL` set.

- **Check readiness** (needs a database — the dev stack below, or the Cloud SQL Auth Proxy): `curl -i http://localhost:8000/api/health/ready` → `200` `{"status":"ready"}`; with no reachable database, `503` `{"status":"unavailable"}`. The body is a fixed status enum and carries no diagnostics by design; the `readiness.probe` log line carries the bounded `failure_class` (`config_invalid` / `connect_failed` / `query_failed`) that tells you which.

### Dev stack (docker-compose — dev only)

A dev-only `docker-compose.yml` (repo root) brings up `/api` alongside a local Postgres 16 + pgvector for parity with the production store. It is **not** a deploy artifact — production uses managed Cloud SQL (ADR-008, see "Live-infra divergence").

- **Up**: `docker compose up --build`. Brings up `db` (`pgvector/pgvector:pg16`, pgvector extension enabled via `scripts/dev/init-pgvector.sql`) and `api` (built from `api/Dockerfile`).
- **Check**: `curl http://localhost:8080/api/health` → `{"status":"ok","service":"theygrow-api"}`.
- The `db` service only enables the pgvector extension; the episodic schema comes from Alembic — `alembic upgrade head` from `api/` with `DATABASE_URL` set (three revisions have landed: `source_messages`; `notes` + `event_chunks`; the per-chunk `vector(1536)` embedding). Since A3-P2 the served surface opens a connection too, from `/api/health/ready` — `curl http://localhost:8080/api/health/ready` → `{"status":"ready"}` against this stack. It needs no migration: the probe is `SELECT 1`.
